## 角色卡

### 任务 1：探查 oldLogger 的全部调用点
- **角色**：只读探查员，负责定位旧日志接口的全部调用位置
- **模型 / effort**：Haiku 5.5 / medium
- **目标**：列出 `src/` 和 `server/` 下所有调用 `oldLogger` 的位置，按文件分组，标出每个调用点的参数以及是否使用自定义 formatter
- **输入**：仓库根目录；`src/`、`server/` 两个目录；可运行 `grep -rn "oldLogger" src server` 辅助检索
- **约束**：只读，不修改任何文件；不执行安装、构建或测试；结果按文件路径排序，不要遗漏测试文件
- **完成标准**：`grep -rn "oldLogger" src server` 的每个命中都能在清单中找到对应条目；使用自定义 formatter 的调用被单独标出
- **返回格式**：Markdown 清单，每行 `路径:行号 — 参数摘要 — 是否自定义 formatter`；末尾附总命中数。正文不超过 300 字，清单不限
- **升级阶梯**：补一条 grep 交叉核对命令 → effort 升到 high → 换 Sonnet 5.5 / medium
- **选型理由**：任务明确、出错代价低、结果可核对，本质是“找到并报告”，定 T0

### 任务 2：按清单替换并适配 formatter
- **角色**：实现者，负责按清单完成日志接口替换
- **模型 / effort**：Sonnet 5.5 / medium
- **目标**：把 `utils/` 下的 `oldLogger` 调用全部替换成 `newLogger`，保持日志级别和输出字段不变；带自定义 formatter 的地方按新接口逐一改写
- **输入**：任务 1 的清单；`utils/` 目录；`newLogger` 的接口定义与现有用法；项目现有测试
- **约束**：只改 `utils/` 下的文件；不改变日志级别与输出字段；不引入新依赖；沿用现有代码风格
- **完成标准**：`grep -rn "oldLogger" utils/` 无输出；`npm test` 通过；`npm run build` 通过
- **返回格式**：改动文件列表 + 每个 formatter 特例的处理说明 + 命令输出摘要，不超过 200 字
- **升级阶梯**：先补 formatter 行为的测试 → effort 升到 high → 换 Opus 5.5 / medium
- **选型理由**：规格已经写死、改动局部、有测试和构建可自动验证，定 T1

### 任务 3：为日志适配层补单元测试
- **角色**：测试员，负责为新日志适配层补齐单元测试
- **模型 / effort**：Sonnet 5.5 / medium
- **目标**：覆盖默认格式、自定义 formatter、错误对象序列化三种情况，每类至少一个用例
- **输入**：日志适配层源码；现有测试目录与测试框架配置；任务 2 的改动
- **约束**：只新增测试文件，不改生产代码；测试不依赖网络、真实时间和本机路径
- **完成标准**：`npm test` 全部通过；三类情况各有独立用例；测试能捕获 formatter 回归
- **返回格式**：测试文件路径 + 用例清单 + `npm test` 结果摘要，不超过 200 字
- **升级阶梯**：补覆盖率检查命令 → effort 升到 high → 换 Opus 5.5 / medium
- **选型理由**：任务明确、局部、可用 `npm test` 自检，定 T1

### 任务 4：排查设置页偶发白屏
- **角色**：调试者，负责定位设置页偶发白屏的根因并修复
- **模型 / effort**：Opus 5.5 / high
- **目标**：找出白屏的触发条件和根因，给出最小修复并实施
- **输入**：`src/pages/settings/` 下相关组件；控制台报错 `Cannot read properties of undefined`；“刷新几次后出现”的复现线索
- **约束**：先从代码路径或复现证明根因，再做最小改动；不顺带重构其他页面；不吞掉错误
- **完成标准**：给出可复现步骤或代码级因果链；修复后构建通过，设置页连续刷新 20 次无白屏；补充防回归测试，或说明无法自动化的原因
- **返回格式**：根因结论（不超过 100 字）+ 证据（文件:行号）+ 修复摘要 + 验证结果，总长不超过 300 字
- **升级阶梯**：补复现脚本或临时错误上报 → 保持 high → 换 Fable 5.2 / medium
- **选型理由**：原因不明、需要调试判断，出错代价中且难以自动验证，定 T2 并升一档 effort

### 任务 5：更新 README 日志接入说明
- **角色**：文档员，负责更新日志接入文档
- **模型 / effort**：Sonnet 5.5 / high
- **目标**：在 README 中补充 `newLogger` 的用法、迁移前后对照和常见错误
- **输入**：`README.md`；`newLogger` 接口与任务 2 的改动；任务 1 的清单
- **约束**：只改 README 的日志章节；不夸大、不编造行为；命令和代码块可直接复制
- **完成标准**：README 中能查到 `newLogger` 用法与迁移步骤；示例代码与当前接口一致；代码块闭合
- **返回格式**：改动章节标题 + 新增内容摘要，不超过 150 字
- **升级阶梯**：补示例代码的可运行验证 → 保持 high → 换 Opus 5.5 / medium
- **选型理由**：规格明确、局部、可人工核对；按参考文件，文档类任务用 Sonnet 并配 high，定 T1

### 任务 6：审查任务 2、3、5 的 diff
- **角色**：审查员，负责审查日志相关改动
- **模型 / effort**：Opus 5.5 / medium
- **目标**：审查任务 2、3、5 的 diff，找出行为变化、遗漏调用点和测试缺口
- **输入**：`git diff`（仅限任务 2、3、5 涉及的路径）；任务 1 的清单；任务 2 的返回说明
- **约束**：只读审查，不直接改代码；只报有证据的问题；按严重程度排序
- **完成标准**：每个改动文件都被看过；所有 formatter 特例都有对应测试或说明；给出通过或不通过的明确结论
- **返回格式**：问题列表（文件:行号 + 问题 + 建议），无问题时写“通过”；不超过 300 字
- **升级阶梯**：补运行测试与构建的完整输出 → effort 升到 high → 换 Fable 5.2 / medium
- **选型理由**：代码审查属于 T2，需要跨文件判断；只读变更部分，token 消耗可控

### 任务 7：盘点页面组件里的字符串拼接日志
- **角色**：只读探查员，负责盘点页面组件里的旧式日志
- **模型 / effort**：Haiku 5.5 / medium
- **目标**：通读 `src/pages/` 下所有页面组件，找出仍用手写字符串拼接或直接 `console` 输出的位置，产出待改清单
- **输入**：`src/pages/` 全部组件；`newLogger` 的用法示例
- **约束**：只读，不修改文件；不把已经是结构化日志的调用列入；按文件分组并给出预计改动量
- **完成标准**：`src/pages/` 下每个文件都被检查过；清单包含 `路径:行号` 与现有写法
- **返回格式**：Markdown 清单 + 每个文件一行结论，不超过 400 字
- **升级阶梯**：补 grep 交叉核对 → effort 升到 high → 换 Sonnet 5.5 / medium
- **选型理由**：本质是“找到并报告”，不产出要合并的代码，读取虽多但不需要判断，定 T0

### 任务 8：按清单统一改结构化日志
- **角色**：实现者，负责页面日志的结构化改造
- **模型 / effort**：Sonnet 5.5 / medium
- **目标**：把任务 7 清单中的页面日志改为 `newLogger` 结构化调用，保持原有信息不丢失
- **输入**：任务 7 的清单；`src/pages/`；`newLogger` 接口；现有测试
- **约束**：只改清单内的位置；不改页面业务逻辑与用户可见文案；不引入新依赖
- **完成标准**：清单中每个位置都已处理；`grep -rn "console\\." src/pages/` 无残留或逐条说明保留原因；`npm run build` 与 `npm test` 通过
- **返回格式**：改动文件与行数统计 + 未处理项及原因 + 构建和测试结果，不超过 200 字
- **升级阶梯**：补页面级冒烟测试 → effort 升到 high → 换 Opus 5.5 / medium
- **选型理由**：规格由清单固定、改动局部、有构建和测试可验证，定 T1

### 任务 9：审查任务 8 的 diff 并验收
- **角色**：审查员，负责页面日志整改的审查与端到端验收
- **模型 / effort**：Opus 5.5 / medium
- **目标**：审查任务 8 的 diff，确认结构化字段完整、没有行为回归，并核对清单覆盖率
- **输入**：任务 8 的 diff 与返回说明；任务 7 的清单；构建与测试输出
- **约束**：只读审查，不直接改代码；逐项核对清单覆盖率；只报有证据的问题
- **完成标准**：清单每一项都能在 diff 中找到对应改动；构建与测试通过；给出通过或不通过的明确结论
- **返回格式**：覆盖率统计 + 问题列表（文件:行号）+ 结论，不超过 250 字
- **升级阶梯**：补一次页面手测 → effort 升到 high → 换 Fable 5.2 / medium
- **选型理由**：跨文件审查加上最终判断，需要判断力，定 T2；只读 diff，成本可控

## 假设与注意事项

- 假设 `newLogger` 已存在且接口稳定；若不存在，任务 2 需先补适配层，档位不变但增加一个子任务。
- 假设项目已有 `npm test` 和 `npm run build` 脚本；没有的话，任务 3 先补测试框架，完成标准改为等效的可执行命令。
- 假设设置页白屏能在本地复现；若不能，任务 4 先加临时日志或错误上报，再定位根因。
- 任务 8 依赖任务 6 的审查结论，避免在前一批改动未确认时继续扩大 diff。
- Claude 平台注意：Haiku 的低价只在输入不超过 100K token 时成立，T0 任务只传目标目录和命令输出，不要整仓读入。
- 主会话在阶段之间换模型会失去提示缓存，建议在阶段断点执行 `/compact` 或新开会话；子代理有独立上下文，不受影响。

## 预计节省

相对“全部任务都用 Opus 5.5 / medium 的主力档”这一基线：9 个任务中 2 个降到 T0（Haiku 5.5，单价约为 T2 的 1/40）、4 个降到 T1（Sonnet 5.5，约为 1/2），只有 3 个审查或调试任务留在 T2。整体开销预计降为原来的四成到一半，且 T0/T1 任务都带可执行的完成标准。实际消耗取决于读取量和重试次数，建议跑完后对照用量统计调整。
