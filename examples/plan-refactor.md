# 单体应用模块化重构

现有系统是一个把订单、结算和消息通知都放在一起的 Node.js 单体应用，部署包越来越大，改一处就要全量回归。这次准备把边界理清，降低后续改动的成本和风险。

1. 梳理当前的模块依赖和调用关系，评估是拆成两个独立服务，还是保留单体、只加模块边界，给出结论和理由。
2. 按上一步的结论搭建模块目录和公共接口层，把跨模块的直接引用改成走接口。
3. 批量把 `src/legacy/` 下所有 `require('../db')` 的写法换成新的数据访问层，这是一批重复度很高的机械替换。
4. 批量给所有 HTTP handler 补统一的错误处理包装，去掉每个文件里重复的 try/catch。和上一步互不影响，可以同时做。
5. 把账单相关逻辑从 web 层迁移到独立的 billing 模块，涉及订单、退款、对账三条链路。
6. 重写结算汇率换算逻辑。这块目前没有任何测试覆盖，改动会直接影响真实金额，需要特别小心。
7. 为 billing 模块补齐回归测试，覆盖汇率换算、退款冲正和并发结算。
8. 跑全量回归测试，并对比重构前后的接口响应时间和内存占用。
9. 最终验收：确认旧入口已下线、监控无异常、文档和部署脚本同步更新。
